# 合成数据规模与并发演示

本增量服务于面试复现，不宣称生产级数据或互联网高并发。原来的演示工作台、120 笔演示订单和模型评测保持可用。

## 数据资产

| 数据 | 规模与覆盖 | 用途 |
| --- | --- | --- |
| 订单 | 10,000 笔，10 租户，1,000 个租户内客户；5 种支付状态、5 种履约状态，10 类状态模板，一年日期跨度 | 数据库规模与业务读取 |
| 政策 | 24 个片段，含原 6 个和 18 个增量；物流争议、退货、换货、发票、优惠券、积分、保修及租户专属窗口 | 有边界的咨询与检索；不增加执行工具 |
| 工作流场景 | 12 类 × 10 租户 = 120 次调用 | 查询、政策、缺金额、缺订单、全额、明确金额、否定、取消、未知订单、无证据、超额、零余额 |
| 并发请求 | 1/10/30 并行，各默认 100 次；另有 30 次相同请求、30 次相同审批 | 跨工单吞吐、幂等与副作用验证 |

全部为第一方合成数据，无真实个人数据。固定 seed=20260915，金额、客户和日期可复现。10,000 行只有 10 类状态模板，不能称为 10,000 个独立语义场景。120 个工作流案例使用确定性 reasoner，不计入真实模型准确率。

订单存入独立 tenant-scale-* 命名空间，订单号 O-SCALE-*；插入冲突 DO NOTHING，不重置已退款余额。原演示数据不被覆盖。扩展政策以独立 manifest 选择，规模脚本实际使用该版本；默认工作台仍使用原政策版本。

## 复跑

在仓库根目录，先验证数据生成：

```powershell
uv run python scripts/ticketpilot_scale_demo.py --dry-run
```

首次创建独立本地数据库（示例密码仅用于此本地合成演示）：

```powershell
docker run --name ticketpilot-scale-postgres -e POSTGRES_PASSWORD=scale-local-only -e POSTGRES_DB=ticketpilot_scale -p 127.0.0.1:55439:5432 -d postgres:16
```

等待数据库就绪后执行；已有容器时用 docker start，不重复创建：

```powershell
$env:TICKETPILOT_SCALE_DSN='postgresql://postgres:scale-local-only@127.0.0.1:55439/ticketpilot_scale'
uv run python scripts/ticketpilot_scale_demo.py --output ../../outputs/2026-09-15/intermediate/scale-run-new.json
```

输出路径必须不存在。脚本应用迁移、幂等插入订单、运行场景及并发实验、核对不变量，保存逐次状态/耗时/工单编号和聚合报告。重复运行不会重复插入订单，但会新增带唯一实验请求键的工单与审计，每轮批准测试会扣一次 0.01 元 Mock 金额；历史测试记录保留。

数据库绑定 127.0.0.1:55439，不修改原 5432 数据库和 8080 后端。演示后可 docker stop ticketpilot-scale-postgres；数据随容器保留，下一次 start 后可查。不要对生产数据库运行此脚本。

## 测量口径

路径是进程内 TicketService → LangGraph → PostgreSQL 业务表与 PostgreSQL checkpoint。没有 HTTP、网关、Bearer 解析、浏览器或真实 LLM 开销，不应写成 API QPS 或大模型吞吐。

每个连接池上限 10（业务池和 checkpoint 池各一个），分类器人为等待 20ms 以形成重叠。客户端以信号量控制同时执行数；这只是测试驱动，不是服务端限流功能。延迟从获得客户端信号量后开始，包含业务连接池等待，排除客户端排队；吞吐以整个批次的尝试数/耗时计算。P95/P99 为 nearest-rank；每档 100 次、单次短测试，不能推导持续负载容量。

同请求测试允许原结果重放或 STATE_CONFLICT，但必须只有一个 ticket 和 run，数据库按完整请求键复核只创建一张工单。同审批测试要求余额只减 0.01 且 REFUND_EXECUTED 审计只有一条；拒绝请求不等于业务执行成功。

## 面试解释

2026-09-15 本机最终短测结果（每档 100 次）：

| 并发数 | 成功数 | 尝试/秒 | P95（毫秒） |
| --- | --- | --- | --- |
| 1 | 100 | 7.75 | 157.220 |
| 10 | 100 | 9.33 | 1179.590 |
| 30 | 100 | 9.46 | 3470.064 |

120/120 场景通过。30 次同请求：1 OK、29 STATE_CONFLICT，一张工单、一个 run。30 次同审批：1 OK、29 STATE_CONFLICT，余额 1077.59→1077.58，REFUND_EXECUTED=1。两轮短测的吞吐略有波动，不能凭这组结果声称 30 并发更优；10→30 并发主要增加了延迟。

同工单用 active_run_id 与短事务保证一个执行者；跨工单可以并行；同审批由行锁与状态/动作幂等约束防止重复扣款。模型调用不放在数据库长事务里。数据规模增大后仍用 tenant + order_reference 索引过滤，不把所有订单加载进 Prompt。

并发升高未必提高吞吐：数据库写入与 checkpoint、连接池等待都可能限制扩展；只有本机观测不足以定位具体瓶颈。生产扩展的优先顺序是先测 HTTP 全链路和真实模型延迟，再做服务端并发额度、有限排队与超时/429/503、租户限额；有跨进程任务需求才引入队列。真实支付再加供应商幂等、Outbox 和对账。

不因此新增 Redis、Kafka、分库分表或多 Agent。本阶段最重要的是保留真实报告、解释边界、完成口述并投递。
